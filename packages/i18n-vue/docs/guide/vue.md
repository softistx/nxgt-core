# Vue

How to wire `createI18n` into a Vue app, and use `t` and the locale from
templates and code.

## Creating the i18n

```ts
// main.ts
import { createApp } from 'vue';
import { createI18n, detectLocale } from '@nxgt/i18n-vue';
import App from './app.vue';
import en from './locales/en.json';
import fr from './locales/fr.json';

const i18n = createI18n({
	catalogues: { en, fr },
	fallbackLocale: 'en',
	locale: detectLocale(['en', 'fr'], 'en'),
});

createApp(App).use(i18n).mount('#app');
```

| Option | Type | Default | Effect |
| --- | --- | --- | --- |
| `catalogues` | `Catalogues` | — (required) | A catalogue per locale, keyed by BCP 47 tag: `{ en, fr, 'pt-BR': ptBR }` |
| `loaders` | `CatalogueLoaders` | none | A loader per locale fetched on demand: `{ fr: () => import('./locales/fr.json') }` — see [Loading a locale on demand](#loading-a-locale-on-demand) |
| `fallbackLocale` | `string` | the first locale of `catalogues` | The reference every other locale is checked against; one of `catalogues` |
| `locale` | `string` | `fallbackLocale` | The locale to start in; one of `catalogues` |

`createI18n` checks the catalogues ([Catalogues](catalogues.md)) and throws on
the first thing that cannot be right. A wrong option is a `TypeError`.

## `t` in a template

`app.use(i18n)` adds `t` to every component's template:

```vue
<template>
	<h1>{{ t('home.title') }}</h1>
	<p>{{ t('home.greeting', { name: user.name }) }}</p>
	<p>{{ t('home.items', { count: cart.length }) }}</p>
	<p>{{ t('home.sentOn', { at: order.sentAt }) }}</p>
	<input :placeholder="t('home.search')" />
</template>
```

The result is text, and `{{ }}` or a bound attribute escapes it. Never pass
it to `v-html`: an argument would be written as markup.

## `useI18n` in code

```vue
<script setup lang="ts">
import { useI18n } from '@nxgt/i18n-vue';
import { computed } from 'vue';

const { t, locale, setLocale } = useI18n();
const heading = computed(() => t('home.greeting', { name: 'Ada' }));
</script>
```

`useI18n()` works wherever `inject` does: a component's `setup`, a
composable called from one, or `app.runWithContext`. With no i18n installed
it throws.

Destructuring is safe: `t` and `setLocale` hold no `this`. `locale` is a
read-only `Ref`, so read `locale.value` in code and `locale` in a template.

## Switching the locale

```ts
const { locale, locales, setLocale } = useI18n();

setLocale('fr'); // every t re-renders in French
locale.value; // 'fr'
locales; // ['en', 'fr']
```

`t` reads the locale reactively: a template, a `computed` or a `watchEffect`
that calls it runs again on a switch. `setLocale` with a locale in neither
`catalogues` nor `loaders` throws, and the locale does not change. Pass it
something from `locales`, or from `pickLocale`.

`setLocale` answers a `Promise<void>`. For a locale of `catalogues` the switch
has already happened when it returns, and the promise is already resolved:
nothing to `await`. It is only worth awaiting for a locale in `loaders`, below.

## Loading a locale on demand

With every catalogue in `catalogues`, every locale ships in the first bundle.
Give the others as `loaders` instead, and each is fetched the first time
`setLocale` asks for it:

```ts
import { createI18n } from '@nxgt/i18n-vue';
import en from './locales/en.json';

const i18n = createI18n({
	catalogues: { en },
	loaders: {
		fr: () => import('./locales/fr.json'),
		de: () => import('./locales/de.json'),
	},
});
i18n.locales; // ['en', 'fr', 'de']

await i18n.setLocale('fr'); // fetched, checked against en, then switched
```

It is opt-in: without `loaders`, nothing on this page applies. A loader is
any function that answers a promise of the catalogue, or of a module whose
default export is one — what `import()` of a JSON file answers. The record is
plain JavaScript, so it is the same whoever writes it: by hand, as here, or
generated by a build plugin.

It is plain `import()`, and no plugin is ever required: Bun, Vite, webpack
and esbuild import a JSON file as is; plain Node ESM needs the import
attribute, `import('./locales/fr.json', { with: { type: 'json' } })`, and
throws `ERR_IMPORT_ATTRIBUTE_MISSING` without it; Rollup alone needs its JSON
plugin, as it does for any JSON import.

```ts
// Node, without a bundler
const loaders = { fr: () => import('./locales/fr.json', { with: { type: 'json' } }) };
```

### The rules

- **The fallback locale and the start locale are in `catalogues`.** The
  fallback locale is the reference every catalogue is checked against, and
  `createI18n` checks it when it runs; the start locale is rendered at once.
  Either one only in `loaders` is a `TypeError`. To start in a lazy locale,
  start in the fallback locale and `await setLocale(locale)`.
- **A locale in both is already loaded.** Its catalogue from `catalogues` is
  used, and its loader is never called.
- **`locales`** lists the locales of `catalogues` in their order, then the
  ones only `loaders` has, in theirs.
- A wrong `loaders` — not an object of functions, or keyed by something that
  is not a locale — is a `TypeError` from `createI18n`. These checks only run
  when `loaders` is given.

### While a catalogue loads

`setLocale('fr')` checks its argument first: a locale in neither record, or
one that is not a string, **throws** synchronously, as it always has. Then:

- a locale already loaded — in `catalogues`, or fetched before — switches at
  once, and the promise is already resolved;
- a locale not loaded yet runs its loader. Until the catalogue is loaded
  **and checked**, `locale` and `t` stay on the previous locale, so the page
  never shows a half-switched state. Show a spinner from your own flag if
  the wait matters:

```ts
const switching = ref(false);
async function choose(next: Locale) {
	switching.value = true;
	try {
		await setLocale(next);
	} finally {
		switching.value = false;
	}
}
```

- **The last call wins.** `setLocale('fr')` then `setLocale('de')` before
  `fr` arrives ends in `de`, whichever catalogue arrives first; a switch to a
  loaded locale while a load is pending wins too. A catalogue that arrives
  late is kept all the same, so a later `setLocale('fr')` is immediate.
- **One load per locale.** Calls made while a locale's loader is in flight
  share it.
- **A superseded call still settles.** When a later call came in while its
  catalogue loaded, a call whose load succeeds resolves without switching
  (the catalogue is kept), and one whose load fails still rejects with the
  load's error — while the locale stays wherever the later call put it.

### When the load fails

The promise rejects, and the locale does not change:

- `setLocale: the catalogue of fr could not be loaded` — the loader threw or
  rejected (offline, a missing chunk). Its error is the `cause`.
- `setLocale: the loader of fr must answer a catalogue, or a module whose default export is one`
  — a `TypeError`: the loader answered something else, such as a module with
  only named exports.
- `i18n: fr: …` — the catalogue cannot be right, with the same message
  `createI18n` gives for a catalogue in `catalogues`
  ([Catalogues](catalogues.md)).

A failed load is not kept: the next `setLocale('fr')` runs the loader again.
See [Troubleshooting](../troubleshooting.md#setlocale-the-catalogue-of-locale-could-not-be-loaded).

The loader's answer is unwrapped to its `default` export when it is a
module namespace, which is recognised by either of two rules:

- its `Symbol.toStringTag` is `'Module'`, as a native `import()` answers
  under Bun, Node or Vite in development;
- or it mirrors its default export: an object `default`, at least one other
  key, and every other key holding the same value as `default`'s. This is
  what a bundle answers once the tag is gone — `bun build` without
  splitting, `bun build --compile`, Rollup when a JSON file is imported both
  statically and dynamically;
- or it is frozen, with no prototype and an own `default`: Rollup's
  namespace when no top-level key of the JSON is an identifier (all
  kebab-case), which then holds only `default`.

Anything else is taken as the catalogue itself: a plain `{ default: {...} }`
with no other key is a catalogue whose one key is `default`.

### What is cached

- Per i18n, each loaded catalogue: the loader runs once per locale.
- Across every i18n, the check: a catalogue object is checked and compiled
  once per set of `catalogues` it is checked against, in a cache keyed on
  that set's checked reference, then on the catalogue object (weakly, so it
  never outlives either). The same set wrapped anew — `{ en }` built per
  request — is the same set, so `import()` answering the same module each
  time means `fr.json` is checked once, not per request. Two different sets,
  such as `{ en }` and `{ en, fr }`, are each checked once; a new catalogue
  object — another build, a copy — is checked again. As with `catalogues`, treat a loaded catalogue as immutable.

### On a server

Create the i18n per request, and `await setLocale` **before** rendering:

```ts
import { createSSRApp } from 'vue';
import { renderToString } from 'vue/server-renderer';
import { createI18n, parseAcceptLanguage, pickLocale } from '@nxgt/i18n-vue';
import App from './app.vue';
import en from './locales/en.json';

const loaders = { fr: () => import('./locales/fr.json') };

export async function render(request: Request) {
	const locale = pickLocale(
		parseAcceptLanguage(request.headers.get('accept-language')),
		['en', 'fr'],
		'en',
	);
	const i18n = createI18n({ catalogues: { en }, loaders });
	await i18n.setLocale(locale); // without await, the page renders in en
	return renderToString(createSSRApp(App).use(i18n));
}
```

### Under plain Bun

Nothing above needs Vite or Nuxt: Bun imports JSON natively, so a Bun
backend writes the same record and gets the same behaviour — for an e-mail,
say, with `t` and no app at all:

```ts
import { createI18n } from '@nxgt/i18n-vue';
import en from './locales/en.json';

const loaders = { fr: () => import('./locales/fr.json') };

export async function subject(locale: 'en' | 'fr', name: string) {
	const i18n = createI18n({ catalogues: { en }, loaders });
	await i18n.setLocale(locale);
	return i18n.t('mail.subject', { name });
}
```

The package's own suite runs exactly this under `bun test`.

## Remembering the choice

`detectLocale` reads `localStorage.language` first. Write the choice there:

```ts
import { watch } from 'vue';

watch(i18n.locale, (locale) => localStorage.setItem('language', locale));
```

Pass `{ storageKey: 'myKey' }` to `detectLocale` to read another key, or
`{ storageKey: false }` to read none.

## A key computed at run time

`t` throws on a key that is not a message. When the key comes from data,
ask first:

```ts
const { t, has } = useI18n();
const label = has(`status.${order.status}`)
	? t(`status.${order.status}`)
	: order.status;
```

## Rendering on a server

Create an i18n **per request**, with the locale the request asks for; one
shared across requests would switch every visitor at once.

```ts
import { createSSRApp } from 'vue';
import { renderToString } from 'vue/server-renderer';
import { createI18n, parseAcceptLanguage, pickLocale } from '@nxgt/i18n-vue';
import App from './app.vue';
import en from './locales/en.json';
import fr from './locales/fr.json';

const catalogues = { en, fr };

/** `storedLocale`: the visitor's `language` cookie, read however your server reads cookies. */
export async function render(request: Request, storedLocale: string | null) {
	const locale = pickLocale(
		[storedLocale, ...parseAcceptLanguage(request.headers.get('accept-language'))],
		['en', 'fr'],
		'en',
	);
	const app = createSSRApp(App).use(createI18n({ catalogues, locale }));
	return renderToString(app);
}
```

The catalogues are checked once, not per request: the cache is keyed on
the imported catalogue objects, so `{ en, fr }` wrapped anew still hits it.
With `loaders`, `await i18n.setLocale(locale)` before `renderToString` — see
[On a server](#on-a-server). The browser
must start in the same locale, or Vue reports a hydration mismatch: serialise
it into the page and pass it back to `createI18n` there. The
[Nuxt module](nuxt.md) does all of this.

## A property of your own called `t`

A component whose props, `data` or `setup` bindings have a `t` sees its own
in its template, not the global one. That is what makes
`const { t } = useI18n()` in `<script setup>` work, and it is also how a prop
named `t` silently wins.
