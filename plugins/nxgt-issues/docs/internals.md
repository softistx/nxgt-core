# nxgt-issues internals

What the plugin's library holds and how its pieces behave in detail. The
[README](../README.md) is the consumer's page; this file is for whoever changes
the plugin.

## Command details

### ready

`ready` lists the tracking issues whose upstream issue is closed and labelled
`released`. `package` and `version` come from the release step's `Fixed in
<pkg>@<version>` comment when it is the last one and an owner, member,
collaborator or the release bot (GraphQL author type `Bot`, login
`github-actions`) wrote it, from a PR of this or another repository. A refresh
costs two GraphQL calls.

### dashboard

`dashboard [--json]` in full: the `/issues` dashboard: open issues of the allowed owners' non-archived repositories (`NXGT_ISSUES_OWNERS`), grouped by repository and headed by the packages it publishes, each group ranked live marker first (an open tracking issue of some application still links the issue, `●`), then applications affected (tracking links, or the reporter plus the "Another consumer hit this" comments an owner, member or collaborator wrote), then oldest; `⚑` after 14 days without activity; tracking issues themselves are not listed; then a "Merged, awaiting release" section (`is:closed reason:completed label:consumer-report -label:released`: a report closed as not planned or as a duplicate is not waiting for a release; oldest merge first). Three `gh search issues` calls (open issues, open `upstream` tracking issues, closed unreleased reports; the search API allows 30 a minute; a search that returns its 200-result limit adds a "truncated" note) are the dashboard: if one fails the command exits 5 (rate-limited, the shared pause applies) or 6 (gh failed). Up to three GraphQL calls are optional: the duplicate comments of up to 30 open reports (more reports add a note; one that is not counted, or whose alias GitHub answered with an error, shows `affected ?`), and the package names of the repositories that render. The package lookup reads names only: call A (25 repositories a call) reads each root `package.json` and the entry names of `packages/`, call B (at most 100 objects a call) reads exactly `packages/<dir>/package.json` for each directory (directory names are checked against `[\w.-]` first). It is cached 24 hours per repository in `cache/repo-packages.json`, only for a repository answered without an error under its alias; a missing file means the repository publishes nothing; a repository whose lookup failed is cached as failed for an hour (so one slow repository cannot fail every run) and shows under its repository name. A cold run is at most 3 searches and 3 GraphQL calls for a few repositories; with the package map cached, 1 GraphQL call. Each failed optional call adds a note and a warning on stderr, never an exit code. Third-party text goes through the same one-line cleaning and untrusted-data header as the hook's context. `--json` prints `{groups, awaiting, notes}` (no issue bodies)

### markers

`markers [--json] [--exclude <pathspec>]…` in full: every `Temporary, until <upstream>#<n>` marker (`git grep`; each `--exclude <pathspec>` or `--exclude=<pathspec>` becomes an `:(exclude)<pathspec>` so a repository can skip its fixtures and docs examples), judged against this repository's open tracking issues: `ready` (upstream closed and released: remove it), `unresolvable` (bad reference, repository not found, not an allowed owner, archived or issues off), `untracked` (no open tracking issue here links that upstream issue; flagged in a private application), or `waiting` (not flagged). A **public** application has no tracking issues, so its markers read the upstream issue directly (`ready` or `waiting`, with `untracked` only as a note, not a flag). **Known limit:** a package that moved repositories resolves there through the registry's current repository, so a marker written for its old repository reads the new repository's issue of that number; a private application matches its tracking issue by package name and number first and is not affected. Refusing instead is not simple and safe: a public application keeps nothing that names the old repository to compare with. **Exit 1 when any marker is flagged**, 0 when none is, 6 when an upstream issue GitHub could not read leaves a marker `unreadable` (the other markers are still printed; they are not counted as flagged, and the closing line states the unreadable count apart), 2 for a foreign origin, 5 rate-limited, 6 when `git grep` or gh fails; a rate limit or a gh failure is never reported as `unresolvable`. Exit 1 is shared with usage: a CI step runs `markers --json` and treats stdout that is not JSON as a failure. The marker names its upstream as `<npm-name>#n` or `owner/repo#n`; an npm name resolves like `resolve`

### released

`released <pkg@ver> [--json] [--dry-run]` in full: from the library's checkout: the issues the published version fixes get, in this order, the `released` label (created when missing), the close and "Fixed in `<pkg>@<ver>` (#PR)" (once, last: it is the marker); an issue whose `## Versions` section names another package of the checkout is skipped, left to that package's run (never when its Versions also name the released package), only when all hold: rank 0, the fixing PR touched that package's folder, it adds a changeset naming that package, and that package has an earlier tag in this clone (its run reads the log since it); when git cannot say, the issue is handled here; prints the application tracking issues linking them (the sessions to notify). Idempotent; `--dry-run` reads and writes nothing; exit 1 for a malformed `<pkg@ver>`, a package this checkout lacks, or a monorepo root (one with `workspaces`, which is refused and is never a sibling); skipped issues are left out of the printed `notify` list; 2 for a foreign checkout, 5 rate-limited, 6 when a PR or an issue failed (the rest was done)

## The hook's cache

It reads `<home>/cache/<owner>__<repo>.json`, where `<home>` is
`$NXGT_ISSUES_HOME`, else `$CLAUDE_CONFIG_DIR/nxgt-issues`, else
`~/.claude/nxgt-issues`. The folders are created 0700 and every file (stamps and
the temporary file before its rename included) 0600: the cache holds the titles
of private repositories' issues. A home that cannot be written costs the cache,
not the output: the refresh still returns its snapshot and the hook renders it.
The entry is fresh for 10 minutes (2 minutes when it holds an upstream issue GitHub could not read):

| cache | the hook |
| --- | --- |
| fresh | renders it; no gh call |
| stale | renders it with "as of Nm ago" and starts `issues.ts refresh` detached (from the home directory, with bun's `--no-env-file` and the plugin's empty `bunfig.toml`), so the next session sees fresh data; not more than one per minute (a `refreshing` stamp, created exclusively, so hooks starting together spawn one) |
| absent | one inline refresh capped at 800 ms (each gh call at 650 ms, and any call still running is killed before the hook returns, so no `gh` outlives it); if it does not finish, or a gh call is cut at its cap (a timeout, not a failure: no `failed` stamp), prints nothing and starts the same detached refresh, so the next session finds a cache. A fresh `refreshing` stamp (a detached refresh is already running) means no inline attempt at all |
| failure stamp | a refresh that fails (gh missing, logged out, bad answer) leaves a `failed` stamp (in `cache/stamps/`) for 10 minutes: no attempt meanwhile, a stale entry is rendered as it is and an absent one prints nothing |
| rate-limit pause | a stale entry is rendered without a refresh; an absent one prints nothing, with no call |

Fresh entries and stamps aside, a first answer for a repository costs the two
GraphQL calls described in the README.

| `labels.ts` | the labels (`LABELS`), `hasLabel` (a case-insensitive match against a `LABELS` key) and `ensureLabels` |
| `crew-registry.ts` | a read-only copy of nxgt-crew's registry reader and liveness rule |
| `workspaces.ts` | a repository's manifests, their dependencies, and an installed dependency's manifest |
| `deny-sources.ts` | where a filing's deny-list comes from, and the configuration |
| `private-repos.ts` | the deny owners (defaults, `NXGT_ISSUES_OWNERS`, `NXGT_ISSUES_DENY_OWNERS`, the token's organisations), their private repositories, the caches and the refusals when a list is empty, shrunk or too old |
| `report.ts` | the stdin JSON of `file` |
| `cli.ts`, `cli-context.ts`, `filing.ts`, `file.ts`, `file-checks.ts`, `deps.ts`, `deps-behind.ts`, `track.ts`, `sessions.ts` | the commands (`app-side.ts` and `markers-check.ts` above) |

The `issue-body.ts` templates do not scrub. `file` renders the whole body (and
the duplicate comment) and runs `scrub()` on the rendered text, refusing on
`refused`; scrubbing the inputs alone is not enough.

Every invocation of the CLI (the hook, the detached refresh, the skills' commands and `allowed-tools`, the autonomy agents, the `nxgt-package` skill) runs `bun --no-env-file --config=<plugin>/bunfig.toml …`, checked by `scripts/skills.spec.ts`. A dependency name read from a `package.json` is looked up under `node_modules` only if it matches the npm name pattern (`PACKAGE_NAME` in `lib/workspaces.ts`), so a key like `../../x` cannot read a manifest elsewhere.

`scripts/issues.ts` and `scripts/hooks/session-start.ts`, the two entry files, are the only files that build the real runner.
`no-network.spec.ts` fails if any module other than `runner.ts` spawns a
process, opens a socket or calls `fetch` (it reads the library recursively); the
real runner throws in a test run (`NODE_ENV=test`, or a `*.spec.ts` entry file)
unless `NXGT_ISSUES_ALLOW_NETWORK=1`.
