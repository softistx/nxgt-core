# `code-reviewer` in nxgt-data

nxgt-data is the Bun workspace behind the public `@nxgt/*` data-access packages, published to npmjs with changesets: five standalone ones — `@nxgt/drizzle` (with the `./pg` dialect subpath), `@nxgt/meilisearch`, `@nxgt/mongo` (with the `./migrations` and `./gridfs` subpaths), `@nxgt/redis` and `@nxgt/s3` — and five built on siblings: two bridges — `@nxgt/mongo-meilisearch` and `@nxgt/drizzle-meilisearch` — the wiring kits `@nxgt/mongo-kit` and `@nxgt/redis-kit`, and `@nxgt/mongo-search-kit` over both Mongo kits. The Drizzle bridge is deliberately the smaller of the two: `reindexAll` and one call per write, with no `start`, no resume point and nothing followed, because PostgreSQL has no change feed a library could read without owning the deployment. `@nxgt/redis` and `@nxgt/s3` wrap Bun's own `RedisClient` and `S3Client`, so they have **no dependency at all** and are Bun-only by construction. `examples/` holds applications, not packages. Its promise is type safety that is **measured** — what the compiler rejects, proved by `@ts-expect-error` cases — and specs that run against real servers. The worst defects here compile and pass: a refusal the types no longer make, a factory that grew a closure back, a stamp name spelled out as a literal, two copies of a driver class.

## Measure

```bash
find packages/*/src scripts -name '*.ts' ! -name '*.spec.ts' -exec wc -l {} + | sort -rn | head -20
git ls-files 'packages/*/src/**/*.spec.ts' | xargs wc -l | sort -rn | head -15
```

The green bar, as CI runs it (build first, because `exports` points at `dist/`):

```bash
./node_modules/.bin/biome ci
bun run build
bun run typecheck          # includes every package's test/types/
bun run test               # known state in AGENTS.md
bun run verify:artifacts
bun run changeset:status   # skipped on changeset-release/develop
```

You may run the measure commands, `biome ci`, `build`, `typecheck` and `verify:artifacts`. Run the suites **one package at a time** (`(cd packages/<name> && bun run test)` — the `test` script, not bare `bun test`: the ones needing Meilisearch download it first — then the examples, then `bun test scripts`), never all at once: each starts a real server (mongod, Meilisearch, PGlite), and in parallel on a short machine they fail together in ways that look like regressions — `AGENTS.md` describes them. The first run fills `.cache/`: mongod into `.cache/mongodb`, Meilisearch into `.cache/meilisearch`, SeaweedFS into `.cache/seaweedfs`, and a **compiled** Redis into `.cache/redis` — nothing publishes a prebuilt one, so `redis-memory-server` builds it from source, which is minutes on a cold machine and is why it is a script rather than something a spec does. That is expected. Never run `changeset:publish`, `scripts/publish.ts` or `bun changeset`.

## Invariants

- **A sibling is reached only as a published peer.** A package that depends on a sibling declares it by `workspace:^` in **both** `peerDependencies` and `devDependencies`, and imports it by its published name; no tsconfig `paths` to a sibling, no relative import into one, and **no cycle, devDependencies included**. The direction is fixed: `@nxgt/drizzle`, `@nxgt/meilisearch`, `@nxgt/mongo`, `@nxgt/redis` and `@nxgt/s3` depend on **nothing** in the workspace — an import of a sibling from one of those five is a finding. `@nxgt/mongo-meilisearch` sits on two, `@nxgt/mongo-kit` and `@nxgt/redis-kit` on one each, `@nxgt/mongo-search-kit` on four. Anything that joins two packages is a **new package**, never a feature of either.
  `grep -n '"@nxgt/' packages/*/package.json; grep -rn "from '\.\./\.\./\.\./" packages/*/src`
- **`@nxgt/mongo/migrations` and `@nxgt/mongo/gridfs` are subpaths, not packages.** `src/migrations/` and `src/gridfs/` import the rest of `@nxgt/mongo`; nothing else imports either.
- **`@nxgt/mongo/gridfs` writes the chunk documents itself, and that is not an oversight.** Measured on mongodb 7.6.0: **no** `GridFSBucket` call takes a session — not `openUploadStream`, not `openDownloadStream`, not `delete`, not `rename` — so a write through the driver's bucket leaves the transaction it was asked to run in, silently. Code or a review note that "simplifies" the chunk layer back onto `GridFSBucket` is a finding. `files.raw` is the driver's bucket and takes no session either: it is an escape hatch, not a transactional one. Two consequences to watch: the driver's `contentType` option is **dropped without a word**, so the type and the digest live in `metadata.contentType` and `metadata.sha256` and a bucket's schema may not declare either name; and nothing creates the bucket's indexes any more — the driver used to build two of them on its first upload — so `syncIndexes()` or `autoSync` is required rather than an optimisation.
  `grep -rn "openUploadStream\|openDownloadStream" packages/mongo/src`
- **`@nxgt/mongo/gridfs`: a source that was already read is refused, never stored empty.** A transaction the driver retries runs `put`/`putOnce` again over the stream its first run read, and a spent source reads as 0 bytes. `readSource` (`src/gridfs/source/`) throws a `TypeError` naming the call and the bucket on the **first pull**, not at hand-over, so a call refused before reading leaves the source intact. A new source type added to `readSource` that does not go through `pieces` or `once` — the spent checks — is a finding. Its refusals name the source by `shapeOf`, which reads the **prototype's** constructor: reading an own `constructor` property prints whatever the caller's object put there.
- **A cleanup deletes what the call wrote, not what matches its key.** Measured in `@nxgt/mongo/gridfs`: a failed write that cleaned up by `files_id` erased the bytes of whatever was already stored under that id. A failure path that deletes by anything but the ids the call itself recorded is a finding. The same shape in the other direction: a "remove the copy that is not mine" reconciliation run twice at once removes **both**.
- **A deduplicating write elects on the server, never on a rule each caller works out for itself.** An order every caller computes the same way does not settle it either, whatever the key: a document becomes visible when it is committed, not when it is written, so the copy that is first by any client-side key can be the last one anybody can see, and every caller then finds itself first. Measured in `@nxgt/mongo/gridfs`, and released as a defect: `(uploadDate, _id)` left two copies under two different ids and told all three callers their bytes were safe. `putOnce` now stores a file under the first twelve bytes of its sha256, so the copies collide on the unique `{ files_id, n }` index and then on `_id`. It follows that it creates that index itself whatever `autoSync` says, that `drop()` forgets the memo of having created it, and that **no call removes a `files` document it did not write**. A reconciliation that resolves a race by deleting is a finding.
- **`@nxgt/drizzle`: an update never moves a row's key.** `update` and `updateMany` refuse any primary-key column in the patch with an `ArgumentError` at run time (`stamp-writes.ts`), and the types refuse `TKey`, the column `primaryKey` names, with a `test/types/` case; the other columns of a composite key are refused at run time only, since Drizzle's column types do not say which columns a key covers. `upsert` keeps the key the same way: its update half leaves **every** column of a composite key untouched, as it does the creation stamps (`kept` in `operations/upsert.ts`). A write path that sends a patch without that check, or an update half that sets a key column, is a finding.
- **A dialect is a subpath, not a package.** What is dialect-free (errors, cursor, page shapes) lives in `@nxgt/drizzle` itself, and every dialect throws those same classes.
- **One driver, one `ObjectId`.** The `mongodb` devDependency pin stays inside the range `mongodb-memory-server-core` depends on; a tree with two drivers is a finding.
  `ls node_modules/.bun | grep '^mongodb@'`
- **Peers and pins move together.** `drizzle-orm`, `meilisearch`, `mongodb` and `zod` are peers with the ranges `AGENTS.md` gives, and exact devDependency pins inside them. A peer raised without its pin, or the reverse, is a finding.
- **A library never bundles its dependencies.** `build.ts` keeps `packages: 'external'` and `splitting: true`.
- **`export * from '<external package>'` only in an entry point**, and every entry in `nxgt.entrypoints` has a matching `exports` key, and the reverse.
  `grep -rn "export \* from '[^.]" packages/*/src`
- **A public method that refuses something has a `@ts-expect-error` case** in its package's `test/types/`. A *missing* case is the risk: a stale one already fails `typecheck`. Where a refusal is runtime-only, the README must say so.
- **`@nxgt/mongo`: nothing spells a stamp's name.** Every behaviour reads field names from `ctx.stamps` / `definition.stamps` (and, in types, from `StampNameOf` / `StampNamesOf`). A literal `'deletedAt'`, `'version'`, `'createdBy'`… used as a **field name** — a document key, a filter, an update path — is a finding, because a renamed stamp would then be a lie. The grep also finds the legitimate uses; report only the field-name ones. Legitimate: the *kind* passed to `StampNameOf<Def, 'updatedAt'>` or `IfStamp<Def, 'deletedAt', …>`, the defaults in `STAMP_FIELDS`, comments and specs.
  `grep -rnE "'(createdAt|updatedAt|deletedAt|version|createdBy|updatedBy|deletedBy)'" packages/mongo/src --include=*.ts | grep -v spec`
- **`@nxgt/mongo`: the context holds data, not closures.** A function-valued field on `CollectionContext` other than the caller's own hooks is a finding, and so is a `createContext` that returns helpers.
- **`@nxgt/mongo`: subjects import one way.** In `src/collection/`, `operations/` never imports `hooks/`; only `get-collection.ts` and `types.ts` reach into every subject; the one root import of a subject is `context.ts` → `hooks/sets`.
  `grep -rn "from '\.\./hooks" packages/mongo/src/collection/operations`
- **A refactor leaves the specs alone.** A spec that changed in a `chore:` commit means behaviour moved. A refactor is its own PR, with a patch changeset, and identical test counts on both sides.
- **A package keeps its own errors**, and depends on no exception package. Each bridge throws its own `SearchSyncError`, wrapping its siblings' errors as `cause` — two classes, one per package, not a shared one; the Drizzle bridge's has no `HISTORY_LOST` or `RUNNING`, since nothing is followed.
- **A refusal names the call and the thing it was on — and names the call a *consumer* wrote.** Several calls in each of these packages take options under the same names (`page`, `pageSize`, `limit`, `after`), so `limit must be an integer of at least 1` is true and useless: nothing in a log line says which listing of an application produced it. The message opens with `<method> on "<collection|table|bucket>": …`, or, for a cursor, keeps `Invalid cursor` in front and puts the origin after it (`Invalid cursor in paginateByCursor on "posts": …`) so the searchable part stays first. The name is the **method a consumer typed**, not the internal function behind it: `paginate on "uploads"`, never `paginateFiles`, which sends them looking for something their code does not contain. A shared guard therefore takes an optional trailing `where` argument and the caller supplies it (`pageWindow`, `cursorLimit`, `decodeCursor` in both `@nxgt/drizzle` and `@nxgt/mongo`); a public paginator with no table of its own takes the name as an option (`PaginateQueryOptions.name`). A new refusal on a call that shares option names with another, and no origin in its sentence, is a finding.
  `grep -rn "throw new RangeError\|InvalidCursorError(" packages/*/src`
- **A message reports a shape, never a value.** What a refusal describes came from a document, a transform or a client, and can hold anything those held — a token in a metadata field, a customer's row. So the sentence says `an array`, `a string`, `null`, `no data field`, and the identifiers it does print are the ones that are structure: a collection name, a bucket name, a chunk number, an `_id`. A message interpolating an unvetted value is a finding. (`JSON.stringify` of a *caller-declared* key, such as the primary key the transform set, is not: it is the caller's own configuration.) The same goes for a server's sentence: `@nxgt/meilisearch`'s `TASK_FAILED` message carries only the task's uid, the call (a `TaskCall` literal, the method a consumer wrote), the index and `error.code`, because Meilisearch quotes the filter or the document id it refused; the sentence stays on `cause` and `task.error`. A new message that embeds `task.error.message` is a finding.
- **`process.emitWarning` is the one warning channel, and nothing else logs.** A package with something to say and nothing to refuse — a GridFS bucket whose missing chunk index makes every read a collection scan — emits one `process` warning with a `code` of its own (`NxgtGridFSMissingIndex`), and a `console.log`/`console.warn` or an injected logger anywhere in `packages/*/src` is a finding. One exception, deliberate: `@nxgt/redis`'s `subscribe` defaults `onError` to a `console.error`, because a listener's throw has nowhere to go and Bun ends the process on an unhandled rejection — that is a callback the caller replaces, not a package deciding to write, and the last-resort `console.error` around `onError` itself exists so a logger with a dead transport cannot end the process through the handler meant to prevent it. The promise attached to it is **once per subject for the life of the process**, so the memo is a module-level `Set` keyed by the subject's own *names* — `<database>:<bucket>` — never by an object: measured on mongodb 7.6.0, `client.db('app') !== client.db('app')`, so a `WeakMap` keyed by the `Db` warns once per call site instead. The memo has no exported reset, because a reset written for the tests is a reset an application can call; a suite that wants to observe the warning binds a subject of its own. A warning never throws and never delays the call it is about: the probe runs **beside** the work, is added to the memo before its `await` so two racing calls probe once, and is forgotten when it fails so the next call tries again.
  `grep -rn "console\.\(log\|warn\|error\)" packages/*/src`
- **`@nxgt/mongo-meilisearch`: the context holds data**, plus the caller's `transform` and `toIndexId` as given; the one widening from the caller's types is in `create-search-sync.ts`. An `as never` elsewhere is a finding.
- **`@nxgt/mongo-kit`: the kit is immutable, and closes only what it opened.** `as`, `withSession` and `transaction` build a kit on a **new context**, never mutate one; the clients come from `connectMongo`, whose holds are counted per URI, and a client the application passed in is never closed.
- **`@nxgt/mongo-kit`: a bucket is a scope property in the kit's session; `syncBuckets()` is not.** The config's `buckets` wire `@nxgt/mongo/gridfs` buckets beside the collections (`bucketAt` in `kit/scope.ts`, one cache with the collections), built with the kit's `session` and the database's `autoSync`, so a file write joins a transaction; `bucketOptions` may not carry `session` or `autoSync`, and a key wired as both a collection and a bucket is refused. `kit.syncBuckets()` (`syncKitBuckets` in `kit/sync.ts`) runs **outside** the session, as `sync` does: mongod refuses `createIndexes` in a transaction. The trap to keep documented: `autoSync` on the first transactional upload creates the chunks collection after the transaction's snapshot, the commit fails with **code 112**, and the driver re-runs the body — a stream source is spent by then, so the retried `put` is refused and the transaction commits nothing. A bucket built without the session, or docs that drop "call `syncBuckets()` at start-up", is a finding. The buckets come from the `./gridfs` subpath of the same peer, so they add no dependency.
- **`@nxgt/mongo-search-kit`: it does not own the Mongo kit.** Closing it stops the syncs and nothing else. Its config type infers `I` from each entry's **`index` alone** (`IndexMap<I>`): widening that to infer the whole entry defeats contextual typing of an inline `transform`, which then comes back `any`, and is a finding even though it compiles. It **refuses a key the kit wires a bucket under**, by the definition's shape — a collection's has a `schema`, a bucket's has none — since a bucket carries a `definition` too; a check back on `'definition' in` alone is a finding.
- **A promise a package owns is taken where it is created.** In Bun a rejection with no handler **ends the process**, and attaching one *later* than the rejection does not save it. A loop that starts several long-lived things and only attaches `.catch` after the loop is a finding, even when every exit path attaches one: the window is every later `await`. Measured in `@nxgt/mongo-search-kit`, where a later `start` runs a full reindex.
- **A spec that watches a promise reject takes it up before the failure.** The same rule, one level out: hold it where the promise is made — `const closed = rejection(subscription.closed)` — and assert with `expect(await closed)`, never `await expect(p).rejects.…` on a line that comes *after* the one causing the rejection. In that window nobody is waiting, Bun counts the rejection as unhandled, and the test fails with the very error it came to assert: a loaded CI runner fails where an idle laptop passes. Measured on bun 1.4.2: holding `expect(p).rejects.toThrow(…)` across an `await` and finishing it later **never returns** — the whole file runs out of time and the per-test timeout does not fire — so the held form is a plain `.then(onResolved, onRejected)` whose resolved arm throws. A fixture that hands back a long-lived subscription or sync takes its `closed` at hand-over, which is why `@nxgt/mongo-meilisearch`'s specs never had this bug.
- **A `Promise.race` settles once, so it reports one failure.** Code that then treats "this failed" as "this was already reported" loses every failure after the first. Whatever swallows a duplicate must match the **one** the race actually carried.
- **Two `define*` shapes in one package must not be assignable to each other.** Measured in `@nxgt/redis`: a `CacheDefinition` and a `ChannelDefinition` both carry `name` + `schema`, so `publish(client, someCache, …)` compiled and published on a channel named after the cache. A `ttl?: never` closes it. Wherever a package has several definition kinds, one must refuse the others structurally, with a `test/types/` case for each direction.
- **`@nxgt/s3`: a guard refuses before anything is sent, and measures what it claims to.** Every `S3Error` is thrown ahead of the request. Watch the measurements the guard rests on: a **`S3File` is a `Blob` whose `size` is `NaN`**, so a size check that returns it passes every body silently — a comparison against a `Blob`'s `size` with no `Number.isFinite` is a finding. A content type is compared on its **essence** (parameters and case dropped), because `Bun.file('a.csv').type` is `text/csv;charset=utf-8` and a text `Blob` adds the charset itself.
- **`@nxgt/s3`: a presigned PUT constrains the key and the deadline, and nothing else.** `presign`'s `type` only adds `response-content-type`, S3's override for what a *download* is labelled; `X-Amz-SignedHeaders` stays `host`. Any API or prose that offers a content type on a presigned **PUT**, or implies one is enforced, is a finding — measured against a live service, such a URL stores a body of any type, status 200. `presignPost` is the call whose size range and content type the **service** enforces.
- **`@nxgt/s3`: `presignPost` signs its own policy, with a secret no context shows.** Bun has no POST presigning, so the package signs SigV4 itself (`operations/post-policy.ts`, `node:crypto`). The secret lives in a module-level `WeakMap` keyed by the context (`secretOf` in `bucket/context.ts`), **never on the context**: `Bun.inspect` and `JSON.stringify` print a context's fields. And Bun reads `S3_SECRET_ACCESS_KEY`/`AWS_SECRET_ACCESS_KEY` **once, at start-up**, while the context resolves them at bind time, so `post-signer.ts` recomputes the signature Bun put on a throwaway probe PUT URL with that secret and refuses on a mismatch — the form would otherwise be refused only when a browser posts it. The endpoint, region and access key id are read off that probe, not worked out again. A secret field on the context, or a signer that skips the drift check or re-derives Bun's endpoint rules, is a finding. Its refusals follow the shape rule to the letter: a size or type from the options is reported by `shapeOf`, never quoted. Shared guards (`checkType`, `checkSize`, `checkOption`) take `where` and **end** with `(<call> on "<bucket>")` so their searchable lead stays first; `presignPost`'s own refusals **lead** with `presignPost on "<bucket>":`. A guard call with no `where`, or a quoted value, is a finding.
- **A package whose error class shares a name with the runtime's is discriminated by `instanceof`.** Bun names its own S3 failures `S3Error` too, with S3's codes. Code or docs that branch on `error.name` is a finding; so is a read that turns *every* failure into `undefined` rather than the one code that means "not there".
- **`@nxgt/meilisearch`: `rebuild` never deletes the live index.** It fills `<uid>_next` (a `nextUid` equal to `uid` is refused) and swaps it in — atomic on the server, or a rename when the live index does not exist — then deletes `nextUid`, which after a swap holds the previous documents. No path deletes `uid`. From sending the swap until its task is read back the outcome is **unknown**, and an unknown outcome deletes nothing. `REBUILD_FAILED` wraps everything from creating `_next` through reading back the swap, with the cause on `cause`, and a failed cleanup never hides it. `settle` waits for every task `fill` enqueued and throws for a failed one, since the SDK resolves a failed task like a succeeded one. A delete of `uid`, a cleanup in the unknown window, or a step between creating `_next` and the swap's read-back outside the `try` is a finding.
  `grep -n "deleteIndex\|stop = " packages/meilisearch/src/sync/rebuild-index.ts`
- **`@nxgt/meilisearch`: `multiSearch` is typed per query, and `tenantToken` drops no rule.** `multiSearch` infers the queries as a tuple (`const Queries extends readonly { index: TypedIndex<any> }[]`, not `MultiSearchQuery<any>[]`, which makes every result `any`) and `CheckedQuery` refuses a key `search` does not take; each needs its `test/types/` case. `tenantToken` refuses, with a `TypeError`, a `searchRules` key that is not the uid of one of `indexes` and a `searchRules` object that inherits its rules: a rule that is dropped signs as **"no filter"** on that index. Unmatched or inherited keys that pass silently are a finding. `tenantToken` imports `generateTenantToken` from the SDK's `meilisearch/token` subpath, which the peer range must keep.
- **`@nxgt/mongo-meilisearch`: nothing is recorded that was not sent.** A resume point is saved only after the batch it covers is applied, or, with nothing to send and no change being handled, from the subscription's `position`. A `saveState` that could run before its `send`, or while a change is in its handler, is a finding: the change would never be sent again.

## Structure

- A function over **80** lines, or a source file over **250**. A long file of declarations is not a finding (`mongo/src/collection/types.ts` is one). For a grown factory, the seam is the shape `packages/mongo/src/collection/` follows: a data-only `context.ts`, then plain functions taking it first — `filters.ts`, `documents.ts`, `operations/reads.ts`, `operations/writes.ts`, `operations/paginate.ts`. `@nxgt/drizzle`'s `pg/repository/` is the second one cut that way and the one to compare a third against: `context.ts` (six fields, `actor` the last, no closures, and a `builders(ctx)` that **reads** the loosely typed handles rather than holding a second copy of the database), `filters.ts`, `stamp-writes.ts`, `operations/{reads,writes,upsert,paginate}.ts`, and a `create-repository.ts` whose `build()` only names the methods. A split like this is its own PR with **no spec touched** — the unchanged test count is the only evidence nothing moved — so a spec change in the same diff is a finding.
- A folder past a dozen source files, or files that need a prefix to tell apart, is several subjects.
- Specs are split by subject and live next to the code; `AGENTS.md` lists `@nxgt/mongo`'s. A new subject with no spec of its own is a finding.
- An import carrying a `.js` or `.ts` extension is a finding.

## Deliberate — do not report

From the table in `AGENTS.md`:

- `LICENSE` at the root and in each `packages/*/`.
- `build.ts`, `scripts/`, `.github/`, `biome.json`, `bunfig.toml`, copied from nxgt-http.
- The test servers, copied rather than shared, because a package reaches no sibling's tests and an example reaches no package's: **five** mongod copies (`@nxgt/mongo` and `@nxgt/mongo-kit` as `test/server.ts`, `@nxgt/mongo-meilisearch` and `@nxgt/mongo-search-kit` as `test/mongo.ts`, `examples/hono-api/test/kit.ts`) and **four** Meilisearch ones (`@nxgt/meilisearch`'s `test/server.ts`, and `test/meilisearch.ts` in `@nxgt/mongo-meilisearch`, `@nxgt/mongo-search-kit` and `@nxgt/drizzle-meilisearch`). `@nxgt/drizzle`'s PGlite helper `test/db.ts` is copied into `@nxgt/drizzle-meilisearch` for the same reason, with a one-table schema of its own. Do report a `MONGOD_VERSION` that differs between any of the five, or a fix made in one copy and not the others; CI keys its cache on the hash of all five.
- The Redis test server is copied **twice**, `@nxgt/redis`'s `test/server.ts` into `@nxgt/redis-kit`'s, differing only by a header saying so: keep `REDIS_VERSION` equal in both — `redis-memory-server` compiles the source, so two versions is two builds — and CI keys its cache on the hash of both files and `scripts/redis.ts`. `@nxgt/redis` inverts the usual direction on purpose: `scripts/redis.ts` imports `redisBinary` from `packages/redis/test/server.ts`, so the version and the cache path have one home. `@nxgt/s3` has **one** server and no copy. `@nxgt/s3`'s runs SeaweedFS — **not MinIO**, which is archived and publishes no binary — and its `test/server.ts` carries six measured workarounds as comments. The costliest is **stderr to a file, never a pipe**: 64 KB undrained blocks the writer, which looks like a server that starts and then hangs. A measured comment removed from either file is a finding.
- `batch.ts`, `documents.ts` and `errors.ts` in both bridges, `@nxgt/mongo-meilisearch` and `@nxgt/drizzle-meilisearch`: the chunking by `batchSize`, one `Entry` per id so adds and deletes cannot race, `keyOf` telling `1` from `'1'`, and the `SearchSyncError`/`failed` pair. Do report a fix made in one and not the other. What deliberately differs: the Drizzle `entryOf` takes a row and reads its id through the caller's required `toIndexId`, the batch helpers take a `wait` flag because only `reindexAll` waits there, and its error codes are three, not six (the Mongo bridge has `HISTORY_LOST`, `ID_MISMATCH`, `NOT_A_DOCUMENT`, `RUNNING`, `LEASE_LOST`, `FAILED`). `reindexAll`'s `onPage` calls through a wrapper that makes whatever it throws — a `SearchSyncError` included — this reindex's `FAILED`, since `failed` passes a `SearchSyncError` through unchanged.
- `lease.ts` in `@nxgt/mongo-meilisearch`, after `@nxgt/mongo`'s `migrations/lock.ts` (not exported, so copied): one document timed by `$$NOW`, the holder `host:pid:<ObjectId>`, renewal by an update filtered on the holder, release by `deleteOne` on it. Do report a renewal or release fix made in one and not the other. What deliberately differs: the lease is **taken** by one `findOneAndUpdate` with `upsert` and a pipeline update deciding on `$$NOW` — never `$documents`/`$merge`, whose `aggregate` ate the change-stream specs' failpoints — and a lost lease stops the follower, or a reindex before it removes or records (`confirmLease`, which throws when MongoDB cannot be reached), with `LEASE_LOST`. A destructive step in the bridge's reindex that does not first confirm the lease is a finding.
- `pingDb` in `@nxgt/mongo-kit`'s `kit/ping.ts` races the driver's `ping` against a timer, for a database the configuration handed in: `timeoutMS` does not bound a never-connected client's implicit connect (measured, it waits `serverSelectionTimeoutMS`). A kit-opened database goes through `connection.ping`, so the driver's own `MongoOperationTimeoutError` is kept — a timer put back on every database is a finding.
- `pagination/page.ts` and `pagination/cursor.ts` in both `@nxgt/drizzle` and `@nxgt/mongo`. Do report a fix made in one and not the other. `errors/data-error.ts` is **not** a copy: the classes differ.
- `connection/connect.ts` in both `@nxgt/mongo` and `@nxgt/redis` — 107 of 167 lines identical, the reference-counted client shared per URI. Do report a fix made in one and not the other. `pingClient` in `@nxgt/redis-kit` is a third, deliberate copy of `@nxgt/redis`'s `ping`, code and message included: a client the configuration handed in carries no `ping` of its own, and a health route must read the same answer either way. `@nxgt/s3` deliberately has **no** third copy: S3 is stateless HTTP, so there is no connection to share and nothing to close; a registry appearing there is a finding, not an omission.
- `@nxgt/s3`'s `ObjectPage` is **not** a copy of `CursorPage`: four lines agreeing on a shape so a caller pages the same way, with no logic to keep in step.
- `syncIndex`'s `TASK_FAILED` and `index_already_exists` branches covered by a scripted client: Meilisearch cannot be made to fail a settings task.

## Layering and packaging

- Ten packages: five standalone, then two bridges on two siblings each, two kits on one sibling each, and a kit on four. `@nxgt/drizzle/pg`, `@nxgt/mongo/migrations` and `@nxgt/mongo/gridfs` are subpaths, not packages; `verify:artifacts` loads **thirteen** subpaths in all.
- **A new workspace member needs `bun.lock` in the same branch.** CI installs with `bun i --frozen-lockfile` and refuses before anything runs; the lockfile also decides the peer ranges a publish writes. A new `packages/*` with no lockfile change is a finding.
- **A brand-new package *name* can 404 on npm for about five minutes** after a successful publish, where a new version of an existing package appears at once. An early 404 is not a failed release.
- **`examples/` are applications, not packages**: `private`, unscoped, and invisible to `publish.ts` and `verify-artifacts.ts`, which glob `packages/*/package.json`. They are workspace members so one install covers them, and the root `typecheck` and `test` reach them. An example under `packages/`, or a `private: true` under `packages/`, is a finding. `examples/hono-api` is laid out **by module** — `src/modules/<name>/<name>.{model,service,route}.ts` — and a module **exports** its own `Hono` rather than being handed one; a file that exists only to be a layer across modules is a finding.
- **A changed package needs a changeset, and a released change needs one that names it.** `changeset status --since` fails when a package's files changed and *no* changeset was added on the branch — measured on changesets 3.0.3, the gate is `releasePlan.changesets.length === 0`, not whether a changeset names the package, and the command's own error points at `changeset add --empty`. So a change that reaches a consumer takes a changeset naming the package, and one that cannot — a spec, a comment, anything `tsconfig.build.json` excludes and `files` does not ship — takes `bun changeset --empty`, which says in words why nothing is published. A package change with no changeset at all is a finding; an empty changeset on a spec-only PR is not.
- Changesets, independent versions, `bun publish` through `scripts/publish.ts`; registry configuration in `bunfig.toml`, never `.npmrc`.
- Every package public (never `private: true`), MIT, with its own `LICENSE`; `typescript` is `^6.0.3` everywhere; siblings by `workspace:^`.
- A README is the npm page: sections with an example each, an **API**, a **What does not compile** list where the package has one, and a **Traps** section; no private name.
- Commit types: `feat`, `fix`, `update`, `chore`, `docs`, `typo`.
